# JavaScriptファイル間の変数共有とTurboの罠 完全解説    2026. 7/14

このドキュメントは、「なぜJSファイル間で変数が使えないの？」という疑問から、「Turbo環境でDOM要素を扱う際の注意点」までを、誰でも理解できるように分かりやすく解説します。

## 1. スコープの「壁」- なぜ変数はファイルを超えられないのか？

まず、大前提として、現在のJavaScript（ESモジュール）では、**各ファイルが独立した世界（スコープ）を持っています。**

`top.js`で以下のように変数を宣言したとします。

```javascript
// top.js
const panel = document.getElementById('main_panel');
```

この`panel`という変数は、`top.js`というファイルの中に建てられた「壁」の内側に存在します。そのため、隣のファイルである`memo_saving.js`から`panel`を直接覗き見したり、使ったりすることはできません。



これは、意図しないところで変数が書き換えられてしまうのを防ぐ、JavaScriptの優れた仕組みです。

---

## 2. `window`オブジェクト - ファイル間の「共有スペース」

では、どうすればファイル間で値を共有できるのでしょうか？その答えが`window`オブジェクトです。

`window`オブジェクトは、ブラウザに表示されているページ全体で**たった一つしか存在しない、特別な共有スペース**のようなものです。

```javascript
// top.js
window.isSelecting = false;

// select.js
if (window.isSelecting) {
  // top.jsで設定した値を使える！
}
```

このように`window`にプロパティとして値を追加（`window.isSelecting = ...`）すると、その値はグローバルな共有物となり、どのファイルからでもアクセスできるようになります。

あなたのコードでは、`window.icon_container`や`window.isSelecting`などが、この仕組みを使ってファイル間で共有されています。

---

## 3. DOM要素の扱い - `getElementById`は「その場」で使うのが基本

`panel`や`memo_panel`のようなDOM要素（HTMLの部品）も、`window`を使えば共有できます。しかし、多くの場合、それは最善の方法ではありません。

なぜなら、DOM要素は`document.getElementById('id名')`を使えば、**いつでも、どのファイルからでも、その場で実物を直接取得できる**からです。

`memo_saving.js`が`panel`を使いたいのであれば、`top.js`から値を受け取る必要はなく、自分で`document.getElementById('main_panel')`を呼び出せば事足ります。現在のコードがそうなっているのは、この理由からです。

---

## 4.【最重要】Turbo DriveとDOM参照の「罠」

ここが一番の混乱ポイントです。なぜ「共通のファイルでDOM要素をまとめて管理する」という案が良くないのか、特にTurboを使っているとなぜ問題なのかを解説します。

### 比喩で理解しよう！

1.  **`getElementById`は「写真を撮る」行為**
    `const panel = document.getElementById('main_panel')`というコードは、**「今、画面に表示されている`main_panel`という要素の写真を撮って、`panel`という変数に保存する」**ようなものです。

2.  **Turboのページ遷移は「舞台セットの全交換」**
    Turboは、リンクをクリックしたときなどに、ページの`<body>`の中身を丸ごと新しいものに入れ替えます。これは、演劇で**「舞台セットをガラッとすべて交換する」**のと同じです。


### 罠の発生プロセス

では、この2つが組み合わさると何が起きるでしょうか。

1.  **最初のページ表示時**
    `turbo:load`イベントで`const panel = document.getElementById('main_panel')`が実行されます。
    ➡️ **（舞台Aのパネルの写真を撮りました）**

2.  **ユーザーがリンクをクリック**
    Turboが働き、`<body>`の中身が次のページのものに差し替えられます。
    ➡️ **（舞台セットがAからBに全交換されました。舞台Aのパネルはもう存在しません）**

3.  **次のページで`panel`変数を使おうとする**
    何かのボタンがクリックされ、以前撮った写真が入っている`panel`変数を使おうとします。
    ➡️ **（しかし、その変数が指しているのは、もう撤去されて存在しない「舞台Aのパネル」の写真です）**

結果、存在しない要素を操作しようとするため、何も起こらないか、エラーが発生します。

### 解決策

この罠を回避する方法はただ一つです。

**「舞台セットが交換されるたび（`turbo:load`のたび）に、写真を撮り直す」**

つまり、`document.addEventListener('turbo:load', ...)`のコールバック関数の中で、毎回`document.getElementById(...)`を実行する必要があるのです。これにより、常に「今そこにある最新の要素」を参照することができます。

## 5. 「共通ファイル」案が推奨されない理由

以上の話を踏まえると、「DOM要素の取得を一つの共通ファイルにまとめる」という案がなぜ良くないかが分かります。

### 理由：実行順序という新たな問題

もし`common.js`という共通ファイルを作って、そこで`window.panel = document.getElementById('main_panel')`を実行したとします。

そして、別の`memo_saving.js`が`window.panel`を使おうとします。

ここでも比喩を使いましょう。
*   `common.js` = 「今日のパネルはこれです」と**メモを書く人**
*   `memo_saving.js` = その**メモを読む人**

`turbo:load`の際、**「メモを書く人」が「メモを読む人」より先に動いてくれないと困ります。** もし読む人が先に動いてしまうと、古いメモを読んでしまったり、まだ何も書かれていない白紙のメモを読んでしまったりします。

この実行順序は、`application.js`での`import`の順番に依存します。

```javascript
// application.js

// この順番を常に意識しないといけなくなる！
import "./common" // メモを書く人
import "./memo_saving" // メモを読む人
```

ファイルが増えれば増えるほど、この「依存関係の順番」を管理するのは非常に面倒になり、バグの温床になります。

---

## まとめ

*   **基本はスコープの壁:** 変数はファイル内で独立している。
*   **共有は`window`で:** ファイルをまたぐ値の共有には`window`オブジェクトを使う。
*   **DOM要素は使う側がその都度取得:** `document.getElementById`は、Turbo環境では`turbo:load`のたびに実行するのが最も安全でシンプル。依存関係の問題も発生しない。

したがって、現在の「各ファイルが必要なDOM要素をその都度取得する」という実装は、非常に堅牢で理にかなった方法と言えます。
