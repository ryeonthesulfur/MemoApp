# Rubyの`private`と「レシーバ」の解説  260914

`Folder#duplicate_into`が`private`のままだとエラーになったバグをきっかけに、「レシーバとは何か」「`private`は何を見て許可/禁止を判断してるのか」を整理する。

---

## 1. 「レシーバ」とは何か

**レシーバとは、メソッドを呼び出す時に、そのメソッドを「持ってる側」として指定するオブジェクトのこと。** `.`の左側に書かれているもの。

```ruby
"hello".upcase
```

この場合、`"hello"`が**レシーバ**。「`"hello"`という文字列に対して、`upcase`というメソッドを呼んでいる」という意味。

```ruby
child.duplicate_into(new_folder.id)
```

この場合、`child`が**レシーバ**。「`child`というオブジェクトに対して、`duplicate_into`というメソッドを呼んでいる」という意味。

**レシーバを省略した場合**

```ruby
def a
  b   # レシーバが書かれていない
end
```

このように`.`を付けずにメソッド名だけを書いた場合、Rubyは自動的に「**今動いてる自分自身(`self`)**」をレシーバとみなす。つまり`b`は、実は`self.b`と書いてるのと同じ意味。ただし文字としては省略されている。

---

## 2. `private`が実際に見てるのはどこか

`private`が付いたメソッドについて、Rubyが確認してるのは**たった1つ**。

> **呼び出す時に、レシーバを明示的に書いているか(`.`を使っているか)、それとも省略しているか**

以下の表がすべて。

| 呼び方 | レシーバ | privateメソッドとして許されるか |
|---|---|---|
| `b`(レシーバを省略) | 暗黙的に`self` | ○ 許される |
| `self.b`(Ruby 2.7以降の特例) | 明示的だが`self`自身 | ○ 許される |
| `other.b`(`other`は別の変数) | 明示的な`other` | ✕ 許されない |
| `child.b`(`child`が自分と同じクラスのインスタンスでも) | 明示的な`child` | ✕ 許されない |

**同じクラスのインスタンスかどうかは、一切関係ない。** 見ているのは「`.`を付けて明示的に呼んでるかどうか」だけ。

---

## 3. 質問への回答

> ある`b`というメソッドの中で、特定のインスタンスに対して別のメソッド`a`を呼び出すことが`private`の中ではダメだという話ですか?

**はい、その理解で合ってます。** `a`が`private`な場合、`b`の中で`何らかのインスタンス.a`という、レシーバ付きの呼び方をするとエラーになります。

> また、そういう書き方は`private`の外ないしは`private`がない状態であれば成立するという理解でいいですか?

**これも合ってます。** `a`が`private`ではなく、普通の(公開された)メソッドであれば、`何らかのインスタンス.a`という書き方は、`private`が関係する制約を受けず、問題なく呼び出せます。

### なぜ`private`はこのルールになっているのか

**`private`が守ろうとしてるのは、「このメソッドは、自分自身の内部処理のためだけに存在していて、他の誰か(他のインスタンスも含む)から`.`を付けて名指しで呼ばれることは想定していない」という宣言。**

具体的に、これが無いと何が困るのかを考える。

もし`private`が「同じクラスのインスタンス同士なら`.`付きで呼び合ってもOK」というルールだったとする。すると、あるクラスの内部だけで使うつもりだった細かい手順(例えば「途中の計算結果を一時的にまとめる」ような、外に見せる必要のない処理)を、**同じクラスの別のインスタンスから自由に呼べてしまう**ことになる。そうなると:

- そのメソッドは「本当に自分専用の内部処理」なのか、「実は他のインスタンスからも頼りにされてる、事実上の公開処理」なのか、コードを読むだけでは分からなくなる
- 後で「この内部処理、ちょっと名前を変えたい/仕様を変えたい」と思っても、**他のインスタンスがこっそり呼んでるかもしれない**ので、気軽に変更できなくなる(いわゆる「密結合」が生まれる)

Rubyの`private`が「同じクラスかどうか」ではなく「レシーバを省略してるかどうか」で判断するのは、**「他人(他のインスタンス)に対して、その内部処理をやらせる/使わせることは一切許さない。あくまで“自分が自分に対して”行う処理としてのみ存在を許す」という、より厳格な境界線を引くため**。

### 今回のバグへの当てはめ(なぜ`private`を外すのが正解だったか)

`duplicate_into`は、まさに`child.duplicate_into(...)`という形で、**「他のインスタンス(`child`)に対して、複製という仕事をやってもらう」**という使われ方をしている。これは「自分専用の内部処理」ではなく、**「どのFolderインスタンスに対しても頼める、正式な操作」**という性質を持っている、ということでもある。

なので今回`private`を外したのは、単に「エラーを消すための応急処置」ではなく、「`duplicate_into`は、そもそも他のインスタンスに対して呼びかける、公開された操作として設計されるべきものだった」という、設計上、筋の通った直し方だったと言える。

## 4. 今回のバグへの当てはめ

```ruby
class Folder < ApplicationRecord
  private

  def duplicate_into(target_parent_id)
    # ...
    children.each { |child| child.duplicate_into(new_folder.id) }
    # ...
  end
end
```

- `duplicate_into`は`private`
- `children.each`のブロックの中で、`child`(`self`とは別の`Folder`インスタンス)に対して、明示的なレシーバ付きで`child.duplicate_into(...)`と呼んでいる
- これは「レシーバを省略していない」呼び方なので、`private`のルールに引っかかり、エラーになった

**直し方**: `private`を外して、`duplicate_into`を公開メソッドにした。これにより「明示的なレシーバを付けて呼ぶ」という、この処理に必要な書き方が許されるようになった。

---

## 5. 補足: 「child」という名前や、作成のタイミングは関係ない

**「`children`」はRailsの標準用語ではない**

`children`という名前は、`Folder`モデルで

```ruby
has_many :children, class_name: "Folder", foreign_key: "parent_id", dependent: :destroy
```

と、こちらが**自分で選んだ名前**。Railsが決めた特別な予約語ではなく、`subfolders`でも他の名前でも構わない。親子構造を表す時によく使われる一般的な呼び方ではあるが、Rails固有の特別な意味を持つキーワードではない。

**`duplicate_into`の中の`child`は、「create」で作られた瞬間の話ではない**

```ruby
children.each { |child| child.duplicate_into(new_folder.id) }
```

ここでの`children`は、`self.children`という**DBへの検索(SELECT)**によって取得されたもの。「旅行」フォルダは確かに過去のどこかで(実際にアプリで作られた時、`FoldersController#create`を通じて)保存されたものだが、この行の時点でやっているのは「新規作成」ではなく「既に保存済みのデータを、関連(`has_many`)経由で取ってきているだけ」。

**本当の条件は「作成タイミング」でも「childという名前」でもない**

条件はただ1つ、**「そのオブジェクトが`self`かどうか」**だけ。

- `.new`で今作ったばかりのインスタンスでも
- DBから`.find`や関連(`has_many`など)で取ってきたインスタンスでも
- 「child」という名前が付いていようが、いまいが

`self`以外の何かに対して`.`を付けて呼ぼうとした瞬間、それは「外」からの呼び出し扱いになり、`private`には引っかかる。「作成のタイミング」や「childという名前」自体が条件になっているわけではない。

---

## まとめ

- レシーバ = メソッドを`.`で呼び出す時の、左側にあるオブジェクト
- `private`が禁止してるのは「レシーバを明示的に書く呼び方」。レシーバを省略した(≒`self`に対する)呼び方だけが許される
- 「同じクラスのインスタンスかどうか」は`private`の判断には関係ない
- 別インスタンスに対してメソッドを呼ぶ必要がある処理(今回のような再帰処理など)は、そもそも`private`にできない
