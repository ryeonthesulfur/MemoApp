# フォルダ・メモのコピー機能、実装計画レポート  260913

コピー機能を「見た目だけの複製」から「実際にDBに保存される複製」に格上げするための、実装手順と確認事項のまとめ。

---

## 1. 背景・目的

今の`copy_btn`(`select.js`)は、チェックの付いたアイコンを`icon.cloneNode(true)`でその場に複製しているだけ。サーバーには何も保存されないので、ページをリロードすると複製したはずのアイコンは消える。

これを、実際にRails側でフォルダ/メモのレコードを新しく作る、本格的な「コピー」機能にする。

---

## 2. 現状の問題点

| # | 問題 |
|---|---|
| 1 | DOMを複製してるだけで、サーバーに保存されていない(リロードで消える) |
| 2 | メモのアイコンには`title`しか表示されておらず、`content`(本文)がDOM上に無い。複製するには先にサーバーから本体を取得する必要がある |
| 3 | フォルダを中身ごと複製するには、子フォルダ・孫フォルダ…を再帰的に辿る必要がある。JS側で何度もfetchを往復して実装すると複雑・不安定になりやすい |
| 4 | 複製先が常に`window.icon_container`(メインパネル)固定になっている。本来は元のアイコンがあった場所(メインパネル、または特定のカラム)に複製されるべき |

## 3. 決定済みの方針

- **フォルダをコピーする時、中身(子フォルダ・メモ)も一緒に、再帰的に複製する**(ユーザーとの相談により決定。空のフォルダだけコピーする案は不採用)

## 4. 実装手順

### A. ルーティング追加
`routes.rb`に、フォルダ・メモそれぞれの複製用エンドポイントを追加する。
- 例: `POST /folders/:id/duplicate`
- 例: `POST /memos/:id/duplicate`

### B. `Folder`モデルに、再帰的に複製するメソッドを追加
自分自身 + 自分の`memos` + 自分の`children`(を再帰的に)複製する処理を、Rubyの中で完結させる(JS側でループさせない)。

### C. コントローラーに`duplicate`アクションを追加
`FoldersController`・`MemosController`それぞれに、Bのメソッドを呼ぶだけのアクションを追加する。メモの複製自体は`Memo#dup`で足りる(再帰は不要)。

### D. `select.js`の`copy_btn`処理を書き換え
`icon.cloneNode(true)`をやめて、`fetch('.../duplicate', { method: 'POST' })`を呼ぶ形にする。返ってきたデータを使って新しいアイコンを組み立て、**元のアイコンと同じ場所(メインパネル、または同じカラム)に追加する**(問題点4もここで一緒に直す)。

### E. 名前の重複回避(`_copy(1)`など)
今はJS側で兄弟要素の名前を見て採番している。これをサーバー側に移すか、クライアント側のまま残すかを、Cのタイミングで決める。

**→ 完了。**

- **Bでやったこと**: `_copy(1)`、`_copy(2)`…と番号を付けて新しい名前を決める処理を、`Folder.next_copy_name`・`Memo.next_copy_name`としてRails側に作った。
- **Dでやったこと**: JS側にあった、名前を数えて`_copy(N)`を組み立てる古いコード(`baseName`・`copyCount`)を削除した。複製後は、サーバーが返してきた名前(`saved.name`、既に`_copy(N)`が付いた状態)を、そのまま画面に表示するだけにした。

新しい名前を決める処理自体をRails側(B)に作ってしまい、JS側(D)はその結果を表示するだけにしたので、「どっちに置くか」という選択肢自体が無くなった。

## 5. 確認事項・要検討点(実装前に決めておきたいこと)

| # | 論点 | 選択肢 |
|---|---|---|
| 1 | 名前の採番ロジック(`_copy(1)`)をどこに置くか | **決定: サーバー側でモデルに実装**(下記参照) |
| 2 | フォルダの`color`属性はどう扱うか | **決定: 元のフォルダと同じ色にする**(下記参照) |
| 3 | ルーティングの形 | **決定: `member`ルート**(手順Aで実装済み: `POST /folders/:id/duplicate`・`POST /memos/:id/duplicate`) |
| 4 | 複製処理の失敗時の扱い | **決定: `ActiveRecord::Base.transaction`で囲む**(下記参照) |
| 5 | 複製先のUI挿入位置 | **決定: 判定せず`icon.parentElement`に追加する**(下記参照) |

### 項目2について: 対応策(決定済み)

**決定内容**: フォルダをコピーした時、複製先の色は**元のフォルダと同じ色にする**(新規作成時のようにランダムには選び直さない)。

**実装上の意味**: Railsの`dup`メソッドは、呼び出したレコードの属性(`name`・`color`など)をそのまま引き継いだコピーを作る。つまり`color`を「元と同じにする」というのは、複製処理の中で`color`だけ特別に上書きするコードを書く必要が無い、ということでもある。何もしなければ`dup`が自動的に元の色を引き継ぐので、むしろ一番シンプルな実装になる。

→ **`color`属性は、`dup`に任せてそのまま(元のフォルダと同じ色)にする。特別な処理は追加しない。**

### 項目1について: 対応策(決定済み)

今のJS版の重複チェックは、`window.icon_container`(メインパネル)だけを見ているため、**複製元がカラムの中にある場合、正しく機能しない**(既にある`_copy(1)`を見落として、また`_copy(1)`という名前を付けてしまう)。

一般的なアプリと同じく、名前の重複チェックは「アプリ全体」ではなく**「同じフォルダ(同じ`folder_id`/`parent_id`)の中だけ」**で行うのが自然なルール。これをDOM(今どこが画面に開かれてるか)に頼らず正確に行うには、サーバー側でDBを`folder_id`(または`parent_id`)で絞り込んで検索する必要がある。

→ **名前の採番ロジックはサーバー側(モデル)に実装する。** 判定は「同じ`folder_id`/`parent_id`を持つ兄弟の中で、同じベース名の`_copy(N)`のうち最大の`N`を探し、その`+1`を使う」というロジックにする。

### 項目4について: 対応策(決定済み)

**困る場面**: フォルダの中身(メモ10個・子フォルダ3個など)を再帰的に複製してる途中、例えば7個目のメモで保存エラーが起きたとする。何も対策していないと、1〜6個目は既にDBに保存済み、7個目以降は無し、という**中途半端な状態のまま残ってしまう**。フォルダを開くと、一部だけ複製された壊れたコピーが残る。

**`ActiveRecord::Base.transaction`とは**: 複数のDB操作を1つのまとまりとして扱い、「全部成功する」か「1個でも失敗したら、それまで成功していた分も含めて全部無かったことにする(ロールバックする)」かのどちらかしか起こらないようにする仕組み。銀行振込で例えると、「Aさんの口座から引く」と「Bさんの口座に足す」の両方が必ずセットで成功するか、両方とも無かったことになるか、のどちらかしか許さない、という保証と同じ。

```ruby
ActiveRecord::Base.transaction do
  new_folder = Folder.create!(...)
  memos.each { |memo| new_folder.memos.create!(...) }
  children.each { |child| child.deep_duplicate_into(new_folder) }
end
```

→ **フォルダの再帰的な複製処理は、全体を`ActiveRecord::Base.transaction`のブロックで囲む。** これにより「複製は全部成功するか、1個も残らないか」のどちらかになり、中途半端な複製が残ることを防げる。

### 項目5について: 対応策(決定済み)

**困る場面**: 今の(古い)コードは、複製したアイコンを常に`window.icon_container.appendChild(clone)`でメインパネルに追加している。カラムの中のものをコピーしても、複製はメインパネルに飛んでしまう。「元のアイコンと同じ場所」に追加するには、コピー時に「メインパネルのものか、どのカラムのものか」を見分ける必要があるように思えた。

**実はもっと簡単な解決策がある**: `icon`(コピー元の要素)の`parentElement`(直接の親要素)は、最初から自動的に正しい置き場になっている。

- メインパネルのアイコン → 親は`window.icon_container`(`folder_saving.js`が`window.icon_container.appendChild(new_folder)`で追加してるため)
- カラムの中のアイコン → 親は、そのカラム自身の`folderShowContent`(`folder_columns.js`が`folderShowContent.appendChild(childIcon)`で追加してるため)

```javascript
icon.parentElement.appendChild(clone);
```

と書くだけで、「メインパネルかカラムか」を判定するロジックを一切書かずに、常に元のアイコンと同じ場所に複製を追加できる。

→ **「どっちなのか判定する」処理は書かず、単純に`icon.parentElement`に追加する。**

## 6. 想定されるエッジケース

### 親フォルダと、その中の子フォルダを同時に選択してコピーした場合の二重コピー

選択モードは`getAllIcons()`で「メインパネル + 開いてる全カラム」のアイコンをまとめて対象にしている。もしユーザーが、あるフォルダとその中の子フォルダを**両方チェックした状態で**コピーを実行すると、

1. 親フォルダのコピー処理で、中身(子フォルダ含む)が丸ごと複製される
2. 同時に、子フォルダ単体のコピー処理も別途走る

という2つの処理が両方実行され、結果的に子フォルダが2重に複製されてしまう可能性がある。実装時にこの組み合わせをどう扱うか(許容する/親が選択されてたら子は無視する、など)を決める必要がある。

**対応策(決定済み)**

コピー実行時に、選択されたアイコンの中に「親子関係にあるもの」が含まれていないかチェックする。含まれていた場合は、コピー処理を実行せず、代わりに

- 「二重コピー選択をしています。」というアラートを表示する
- アラートを閉じたら、選択モードは維持したまま、チェックボックスのチェックだけ全部外す(選び直しをさせる)

という形で対応する。
