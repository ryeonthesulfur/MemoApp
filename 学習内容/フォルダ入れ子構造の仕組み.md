# フォルダ入れ子構造の仕組み

フォルダの中にフォルダを作れるようにする(入れ子構造)を、DBでどう表現しているかの解説です。

---

## 結論

**フォルダの入れ子構造は、`folders`というたった1つのテーブルの中で、行同士が`parent_id`を通じてお互いを指し合うことで表現されています。** 「親フォルダ」専用の特別なテーブルや仕組みがあるわけではありません。

---

## 実際のテーブルの中身

「ドキュメント」というフォルダの中に「仕事」、その中にさらに「資料」というフォルダがある、という3階層を作った場合、`folders`テーブルはこうなります。

| id | name | parent_id |
|---|---|---|
| 1 | ドキュメント | `NULL` |
| 2 | 仕事 | `1` |
| 3 | 資料 | `2` |

これを、頭でイメージしてる入れ子構造に対応させるとこうなります。

```
ドキュメント (id: 1, parent_id: NULL ← 親がいない、一番上の階層)
  └─ 仕事 (id: 2, parent_id: 1 ← 「id が 1」の行 = ドキュメント が親)
       └─ 資料 (id: 3, parent_id: 2 ← 「id が 2」の行 = 仕事 が親)
```

## ポイント

- `parent_id`カラムには、**同じ`folders`テーブルの中にある、別の行の`id`**が入る
- 「資料」の`parent_id`が`2`ということは、「`id`が`2`の行(＝仕事)が、自分の親です」という意味
- 一番上の階層(親がいないフォルダ)は、`parent_id`が`NULL`になる

このように、**自分の親が「何行目(何番のid)か」を記録してるだけ**で、入れ子構造そのものを表現できます。これは「自己参照(self-referential)」と呼ばれる、よくあるテーブル設計のパターンです。

---

## マイグレーションでの書き方

```ruby
t.references :parent, foreign_key: { to_table: :folders }
```

- `t.references :parent` → `parent_id`カラムを自動で作る(渡した名前に`_id`が付く)
- `foreign_key: { to_table: :folders }` → 「`parent_id`に入れていい値は、`folders`テーブルに実在する`id`だけ」という制約を付ける。`to_table: :folders`は、「参照先は`folders`ですよ」と明示するためのもの(何も書かないと、Railsは`parent`という名前から`parents`という無いテーブルを参照先だと推測してしまうため)

## モデルでの書き方

```ruby
class Folder < ApplicationRecord
  belongs_to :parent, class_name: 'Folder', optional: true
  has_many :children, class_name: 'Folder', foreign_key: 'parent_id'
end
```

- `belongs_to :parent, class_name: 'Folder', optional: true` → `folder.parent`で、そのフォルダの親フォルダ(1件)を取得できるようにする。`optional: true`は「親がいない(ルート直下の)フォルダもあり得る」という意味
- `has_many :children, class_name: 'Folder', foreign_key: 'parent_id'` → `folder.children`で、そのフォルダの子フォルダたち(複数件)を取得できるようにする
